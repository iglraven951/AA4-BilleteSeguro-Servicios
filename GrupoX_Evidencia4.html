1. INTRODUCCION

El presente documento describe la implementacion final del proyecto BilleteSeguro, un sistema de gestion bancaria desarrollado con Spring Boot y Spring Data JPA. Este proyecto representa la culminacion de un proceso de desarrollo que aplica principios de desarrollo seguro, patrones de diseno de software y arquitectura de soluciones.

BilleteSeguro es una aplicacion web que permite realizar operaciones bancarias fundamentales como gestion de cuentas, depositos, retiros y transferencias, implementando una arquitectura robusta basada en el patron MVC y siguiendo los principios SOLID para garantizar un codigo mantenible y escalable.

El objetivo principal de esta entrega es demostrar la aplicacion practica de los conocimientos adquiridos en el curso, evidenciando el uso correcto de patrones creacionales, de comportamiento y de microservicios, asi como el despliegue exitoso del MVP funcional en un entorno de produccion.

Tecnologias Utilizadas:
  • Java 17 con Spring Boot 3.2.4
  • Spring Data JPA + Hibernate
  • Base de datos H2 (embebida)
  • Thymeleaf para vistas
  • Maven como herramienta de build

3. PRINCIPIOS SOLID APLICADOS

Los principios SOLID son fundamentales para crear software mantenible, escalable y robusto. En el desarrollo de BilleteSeguro, hemos aplicado estos principios de manera consciente para garantizar la calidad del codigo.

3.1 Single Responsibility Principle (SRP) - Responsabilidad Unica

Definicion

Cada clase debe tener una unica razon para cambiar, es decir, debe tener una sola responsabilidad.

Aplicacion en BilleteSeguro

En nuestro proyecto, este principio se evidencia en la separacion clara de capas:

  • Cuenta.java: Solo se encarga de representar los datos de una cuenta bancaria y sus atributos.
  • CuentaRepository.java: Unicamente maneja las operaciones de persistencia de cuentas.
  • BancoService.java: Contiene exclusivamente la logica de negocio bancaria.
  • BancoController.java: Solo gestiona las peticiones HTTP y respuestas.

Importancia

Al separar responsabilidades, si necesitamos modificar la logica de validacion de transferencias, solo tocamos el Service. Si cambia el formato de respuesta de la API, solo modificamos el Controller. Esto reduce el riesgo de introducir errores y facilita el mantenimiento.

3.2 Open/Closed Principle (OCP) - Abierto/Cerrado

Definicion

Las entidades de software deben estar abiertas para extension pero cerradas para modificacion.

Aplicacion en BilleteSeguro

Implementamos este principio mediante el uso de enumeraciones y la posibilidad de extender funcionalidades:

  • TipoCuenta (Enum): Permite agregar nuevos tipos de cuenta (AHORRO, CORRIENTE, PLAZO_FIJO) sin modificar la clase Cuenta.
  • TipoMovimiento (Enum): Facilita anadir nuevos tipos de transacciones sin alterar la logica existente.
  • JpaRepository: Spring Data permite extender funcionalidades de repositorio sin modificar la interfaz base.

Importancia

Si el banco decide implementar un nuevo tipo de cuenta "EMPRESARIAL", simplemente agregamos el valor al enum sin tocar el codigo existente, minimizando el riesgo de afectar funcionalidades ya probadas.

3.3 Dependency Inversion Principle (DIP) - Inversion de Dependencias

Definicion

Los modulos de alto nivel no deben depender de modulos de bajo nivel. Ambos deben depender de abstracciones.

Aplicacion en BilleteSeguro

Spring Framework facilita la aplicacion de este principio mediante la inyeccion de dependencias:

  • BancoService depende de las interfaces CuentaRepository y MovimientoRepository, no de implementaciones concretas.
  • BancoController recibe BancoService a traves de inyeccion por constructor, no lo instancia directamente.
  • Los repositorios extienden JpaRepository, una abstraccion de Spring Data.

Importancia

Gracias a DIP, podemos cambiar la implementacion de la base de datos (de H2 a MySQL, por ejemplo) sin modificar la capa de servicio. Tambien facilita las pruebas unitarias al permitir inyectar mocks de los repositorios.

4. PATRONES CREACIONALES

Los patrones creacionales se enfocan en los mecanismos de creacion de objetos, proporcionando flexibilidad sobre que objetos crear, como crearlos y cuando hacerlo.

4.1 Patron Singleton

Definicion

Garantiza que una clase tenga una unica instancia y proporciona un punto de acceso global a ella.

Aplicacion en BilleteSeguro

Spring Boot implementa el patron Singleton por defecto para todos los beans gestionados por el contenedor de IoC:

  • BancoService: Anotado con @Service, existe como unica instancia compartida por todos los controladores.
  • DataSource: La conexion a la base de datos H2 se gestiona como Singleton, optimizando recursos.
  • EntityManager: Hibernate mantiene una unica instancia del gestor de entidades por contexto.

Importancia

Al tener una unica instancia del servicio bancario, garantizamos consistencia en las operaciones transaccionales y evitamos problemas de concurrencia que podrian surgir con multiples instancias manejando el mismo estado.

4.2 Patron Factory Method

Definicion

Define una interfaz para crear objetos, pero permite a las subclases decidir que clase instanciar.

Aplicacion en BilleteSeguro

Este patron se evidencia en varios componentes del sistema:

  • Generacion de Numeros de Cuenta: El metodo generarNumeroCuenta() en la entidad Cuenta actua como factory method que crea identificadores unicos con formato especifico (YYYYMMDD + 6 digitos aleatorios).
  • Spring Data JPA: Los metodos como save() actuan como factory methods que crean o actualizan entidades segun su estado.
  • Creacion de Movimientos: El servicio utiliza metodos factory para crear diferentes tipos de movimientos (deposito, retiro, transferencia) con la configuracion adecuada.

Importancia

Factory Method nos permite centralizar la logica de creacion de objetos complejos. Si cambian las reglas para generar numeros de cuenta, solo modificamos un punto del codigo.

4.3 Patron Builder (Implicito)

Definicion

Separa la construccion de un objeto complejo de su representacion, permitiendo crear diferentes representaciones con el mismo proceso.

Aplicacion en BilleteSeguro

Aunque no implementamos un Builder explicito, el concepto se aplica en:

  • Construccion de Movimientos: La creacion de un movimiento requiere multiples pasos: establecer tipo, monto, cuenta, saldos anterior y posterior, descripcion y fecha.
  • DTOs (TransferenciaRequest): Los objetos de transferencia de datos se construyen paso a paso con los datos necesarios para la operacion.
  • Respuestas HTTP: ResponseEntity se construye con builder pattern para definir status, headers y body.

Importancia

El patron Builder mejora la legibilidad del codigo cuando creamos objetos con muchos parametros, evitando constructores con demasiados argumentos.

5. PATRONES DE COMPORTAMIENTO

Los patrones de comportamiento se centran en la comunicacion efectiva y la asignacion de responsabilidades entre objetos.

5.1 Patron Observer

Definicion

Define una dependencia uno-a-muchos entre objetos, de modo que cuando un objeto cambia de estado, todos sus dependientes son notificados automaticamente.

Aplicacion en BilleteSeguro

El patron Observer se implementa en el sistema de notificaciones:

  • Sistema de Notificaciones en Tiempo Real: Cuando se realiza una operacion bancaria (deposito, retiro, transferencia), el sistema notifica automaticamente a la interfaz de usuario.
  • Toast Notifications: Los componentes de UI "observan" los eventos del sistema y muestran alertas visuales cuando ocurren transacciones.
  • Persistencia con localStorage: Las notificaciones se almacenan y sincronizan entre pestanas del navegador usando el evento 'storage'.

Importancia

Observer permite desacoplar la logica de negocio de la presentacion. El servicio no necesita conocer como se muestran las notificaciones; simplemente emite eventos que los observadores procesan segun su responsabilidad.

5.2 Patron Template Method

Definicion

Define el esqueleto de un algoritmo en una operacion, delegando algunos pasos a las subclases.

Aplicacion en BilleteSeguro

Este patron se evidencia en la estructura de las operaciones bancarias:

  • Flujo de Operaciones: Todas las operaciones siguen un template: validar - ejecutar - registrar movimiento - actualizar saldo.
  • JpaRepository: Spring Data define templates para operaciones CRUD que extendemos con metodos personalizados.
  • Controladores REST: Siguen un patron comun de recibir request, procesar con service, y retornar response.

Importancia

Template Method garantiza consistencia en las operaciones. Todas las transacciones pasan por las mismas validaciones y generan registros de movimiento, evitando inconsistencias.

5.3 Patron Strategy

Definicion

Define una familia de algoritmos, encapsula cada uno, y los hace intercambiables.

Aplicacion en BilleteSeguro

El patron Strategy se aplica en el manejo de diferentes tipos de operaciones:

  • Tipos de Movimiento: Cada tipo (DEPOSITO, RETIRO, TRANSFERENCIA_ENVIADA, TRANSFERENCIA_RECIBIDA) tiene su propia estrategia de procesamiento.
  • Calculo de Intereses: La seccion de intereses permite diferentes estrategias de calculo (simple, compuesto) intercambiables.
  • Validaciones: Diferentes estrategias de validacion segun el tipo de cuenta y operacion.

Importancia

Strategy nos permite agregar nuevos tipos de operaciones o metodos de calculo sin modificar el codigo existente, siguiendo tambien el principio Open/Closed.

6. PATRONES DE MICROSERVICIOS

Aunque BilleteSeguro es una aplicacion monolitica, su arquitectura incorpora patrones que facilitan una futura migracion a microservicios y que representan buenas practicas de diseno distribuido.

6.1 Patron API Gateway

Definicion

Proporciona un punto de entrada unico para todas las peticiones de clientes, enrutandolas a los servicios apropiados.

Aplicacion en BilleteSeguro

El controlador REST actua como un API Gateway simplificado:

  • BancoController: Centraliza todos los endpoints de la API bajo el prefijo /api.
  • Enrutamiento Unificado: Las operaciones de cuentas (/api/cuentas), operaciones (/api/operaciones) y movimientos (/api/movimientos) se gestionan desde un punto central.
  • Manejo de Errores Centralizado: Los errores se capturan y transforman en respuestas HTTP consistentes.

Importancia

Este patron simplifica la integracion con el frontend, proporciona un punto unico para implementar autenticacion y facilita el versionado de la API.

6.2 Patron Database per Service

Definicion

Cada servicio gestiona su propia base de datos privada, promoviendo el bajo acoplamiento.

Aplicacion en BilleteSeguro

Aunque usamos una base de datos H2 embebida, la arquitectura esta preparada para separacion:

  • Separacion de Entidades: Las entidades Cuenta y Movimiento tienen sus propios repositorios independientes.
  • Relaciones Bien Definidas: La relacion @ManyToOne entre Movimiento y Cuenta esta claramente establecida, facilitando una eventual separacion.
  • Configuracion Externalizada: Los parametros de conexion estan en application.properties, permitiendo cambiar la base de datos sin modificar codigo.

Importancia

Esta estructura permite escalar componentes de forma independiente y facilita la migracion a una arquitectura de microservicios real cuando el negocio lo requiera.

6.3 Patron Repository

Definicion

Media entre el dominio y las capas de mapeo de datos, actuando como una coleccion de objetos de dominio en memoria.

Aplicacion en BilleteSeguro

Spring Data JPA implementa este patron de forma elegante:

  • CuentaRepository: Extiende JpaRepository proporcionando operaciones CRUD automaticas y metodos personalizados como findByNumeroCuenta().
  • MovimientoRepository: Ofrece consultas especializadas para obtener movimientos por cuenta.
  • Abstraccion del Acceso a Datos: El servicio trabaja con interfaces, desconociendo los detalles de persistencia.

Importancia

El patron Repository centraliza la logica de acceso a datos, facilita las pruebas con mocks y permite cambiar el mecanismo de persistencia sin afectar la logica de negocio.

11. CONCLUSIONES

11.1 Cumplimiento de Objetivos

El proyecto BilleteSeguro ha cumplido satisfactoriamente con los objetivos planteados para la Actividad de Aprendizaje 4:

  • Principios SOLID: Se aplicaron correctamente los principios SRP, OCP y DIP, fundamentando su importancia en el desarrollo del software.
  • Patrones Creacionales: Se implementaron Singleton, Factory Method y Builder, mejorando la flexibilidad en la creacion de objetos.
  • Patrones de Comportamiento: Observer, Template Method y Strategy fueron aplicados para gestionar la comunicacion entre componentes.
  • Patrones de Microservicios: API Gateway, Database per Service y Repository preparan el sistema para escalabilidad futura.
  • Despliegue en Nube: El MVP funcional esta operativo y accesible publicamente.

11.2 Lecciones Aprendidas

  • La aplicacion de patrones de diseno desde el inicio facilita significativamente el mantenimiento y extension del codigo.
  • Spring Boot abstrae muchos patrones complejos, pero es importante entender que ocurre "bajo el capo" para tomar decisiones informadas.
  • El trabajo en equipo y la comunicacion efectiva son tan importantes como las habilidades tecnicas.
  • El despliegue en la nube requiere consideraciones adicionales de configuracion y seguridad.

11.3 Trabajo Futuro

Para futuras iteraciones del proyecto, se identifican las siguientes mejoras potenciales:

  • Implementacion de autenticacion y autorizacion con Spring Security
  • Migracion a base de datos PostgreSQL para produccion
  • Containerizacion con Docker para facilitar despliegues
  • Implementacion de pruebas automatizadas con JUnit y Mockito
  • Evolucion hacia arquitectura de microservicios
